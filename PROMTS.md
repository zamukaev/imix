# iMIX — Промпты для Claude Code (по фазам)

Копируй промпты по порядку. Не перескакивай через фазы: каждый следующий срез
опирается на предыдущий. После каждого крупного шага проверяй результат сам,
прежде чем идти дальше.

## Как этим пользоваться

- Промпты внутри фазы давай **по одному**, не пачкой — так Claude Code не
  распыляется и ты успеваешь ревьюить.
- Полезные приёмы Claude Code:
  - **Plan Mode** (`Shift+Tab` дважды) — сначала пусть распишет план без правок.
  - **Checkpoints** — перед большим шагом; `Esc Esc` откатывает, если что-то сломалось.
  - В конце шага проси прогнать `pnpm typecheck` и `pnpm lint`.
- Если ответ уходит не туда — останови и уточни, не накапливай мусор.
- Промпты ниже намеренно не повторяют то, что уже написано в `CLAUDE.md` и
  `ARCHITECTURE.md`. Достаточно попросить прочитать нужный раздел.

## Phase 3 — Админка ◄ текущая

**~~3.1 — Auth~~ ✅**

Сделано: в API модуль `auth` — register / login / refresh / me на двух JWT
(access 15 мин, refresh 30 дней, **разные секреты**), argon2, `JwtAuthGuard`,
`OptionalJwtAuthGuard`, `RolesGuard` + `@Roles()` и `@CurrentUser()`. Первый
ADMIN приходит из сида (`ADMIN_EMAIL` / `ADMIN_PASSWORD`) — через API роль не
получить, DTO регистрации поля `role` не знает и отвергает его.

На web — страницы `/login` и `/register` на обеих локалях, сессия в двух
httpOnly-куках, аккаунт в шапке. `GET /orders/me` есть, страницы для него пока
нет — она в 3.2.

Три решения, которые стоит помнить:

- **Токены не ставит API.** Он отдаёт их в теле, куки ставит уже web через свои
  route handlers в `app/api/auth/*`. Причина простая: разные origin'ы, и куке от
  API понадобился бы `SameSite=None; Secure` — локально это не работает.
- **Подпись на стороне web не проверяется** (`lib/jwt-claims.ts`). Секрет живёт
  только в API, а он проверяет каждый запрос; на витрине это UX-гейт — решает,
  какую ссылку показать в шапке, и ничего больше.
- **Middleware пришлось тронуть уже здесь**, вопреки плану: Server Component не
  может выставить куку, поэтому продлевать сессию больше негде. Без этого через
  15 минут шапка показывала бы «Войти» живой сессии. Гейт роли для `/admin`
  встанет рядом в 3.2.

> ⚠️ Refresh-токен без таблицы: отозвать одну сессию нельзя, только сменить
> `JWT_REFRESH_SECRET` и разлогинить всех. Осознанный размен на время MVP.

**3.2 — Защита и каркас админки**

> Создай защищённую группу роутов `app/[locale]/(admin)` в web. Middleware
> пускает только роль ADMIN, админские эндпоинты API тоже под role-guard
> (клиенту не доверяем). Свёрстай layout админки и дашборд с базовой
> статистикой: количество товаров, заказов, выручка по каждой валюте отдельно —
> складывать RUB и USD нельзя, курса у нас нет.

**3.3 — CRUD товаров и категорий**

> Реализуй в API админские эндпоинты POST/PATCH/DELETE для products, их variants
> и categories. Формы должны требовать **оба языка и обе цены** — это не
> опциональные поля. Эндпоинт POST /upload для картинок (и позже .glb) в
> Cloudinary или S3 — провайдер вынеси за интерфейс. На web — список товаров и
> форма создания/редактирования с вариантами и загрузкой картинок.

**3.4 — Заказы в админке**

> GET /admin/orders + страница списка заказов с фильтром по статусу и сменой
> статуса (например, PAID → SHIPPED). В списке показывай валюту заказа рядом с
> суммой — заказы в разных валютах лежат вперемешку.

**3.5 — Редактируемая главная**

Сделано (до границы авторизации): модель `HomeTile` + две миграции, публичный
`GET /home-tiles?locale=`, сид тайлов, баннеры в `apps/web/public/home/`,
9 e2e-тестов. После 4.2.1 опубликованы все 8 тайлов.

> Осталось после 3.1/3.2 — писать может только ADMIN:
>
> Собери админку `HomeTile`: список с порядком, флагом публикации, шириной
> (FULL/HALF), поверхностью, картинкой, заголовком и подзаголовком на двух
> языках и максимум двумя CTA. Эндпоинты POST/PATCH/DELETE — под role-guard.
> `primaryHref` проверяй по известным маршрутам витрины: ссылка «куда угодно»
> рано или поздно ведёт в 404, а сейчас это нигде не проверяется.

> ✅ Критерий Phase 3: под админом создаю товар с картинками, вариантами, ценами
> в двух валютах и текстами на двух языках → он появляется в витрине на обоих
> языках; вижу входящие заказы и меняю их статус; меняю порядок тайлов на
> главной без деплоя.

## Phase 4 — Дизайн, адаптив и полировка

Здесь витрина перестаёт быть «чисто и минималистично» и получает настоящий
визуальный язык. Референс — `apple.com`, границы описаны в `CLAUDE.md`
(«Design reference») и полностью — в `ARCHITECTURE.md` §5.

**~~4.1 — Дизайн-система~~ ✅**

Сделано: токены (шрифт Inter с кириллицей, типографическая шкала, свой акцент
вместо синего у референса, высоты тайлов), примитивы `Tile` / `TilePair` /
`TileStack` / `Button` / `ButtonLink` в `components/ui/`, контракт `--surface-*`
(тёмный тайл сам переключает цвета контролов), существующие кнопки переведены на
примитив.

Замечание про мелкие устройства на картинках закрыто в 4.2 — см. ниже.

**~~4.2 — Главная как стопка тайлов~~ ✅**

Сделано: главная читает `GET /home-tiles`, группировка пар вынесена в чистую
функцию `toHomeRows` (8 тестов), картинка в `Tile` накрывает весь тайл, а копия
лежит на ней — тайл стал одной поверхностью, без шва. Старая вёрстка (герой +
сетка «Выбор iMIX») убрана, вместе с ней — мёртвый неймспейс `home` из
каталогов сообщений.

Что известно про картинки в `assets/` — мерил, не угадывал:

| Префикс   | Размер    | Отношение | Куда                                  |
| --------- | --------- | --------- | ------------------------------------- |
| `hero_*`  | 6016×1384 | 4.35      | полноширинный тайл, **широкая полоса** |
| `promo_*` | 2524×1160 | 2.18      | половина тайла в сетке 2×2            |
| `promo_iphone_more` | 1404×1160 | 1.21 | половина, но кадр выше              |
| `airtag-*`| 890×890   | 1.00      | не баннер, обычное фото товара        |

> ⚠️ В `hero_*` устройства занимают примерно 20 % ширины по центру и начинаются
> с ~39 % высоты — верхняя треть намеренно пустая, она под текст. Поэтому в 4.2
> картинка накрывает **весь** тайл (`absolute inset-0` + `object-cover`), а
> заголовок лежит на ней. Отдельная текстовая полоса над отдельной картинкой
> оставляет шов: фон тайла и фон кадра никогда не совпадают.

**~~4.2.1 — Расширение каталога~~ ✅**

Сделано: 6 категорий (добавлены `tablets`, `watches`, `audio`, `accessories`),
9 товаров, 20 вариантов — iPad Air 13" M4, iPad Pro 13" M5, Apple Watch
Series 11, AirPods Pro 3, AirTag. Схема не менялась, только сид. Черновые тайлы
опубликованы и получили CTA; все ссылки проверены, каждая отдаёт 200.

> ⚠️ Тайл AirTag не сделан намеренно. Единственное его фото — квадратный
> предметный кадр с объектом по центру: пустой верхней трети нет, копия легла бы
> на устройство. Вместо этого тайл AirPods остаётся без пары и рисуется во всю
> ширину — ровно тем правилом, что заложено в `toHomeRows`. **Кадр для тайла и
> предметная съёмка — не одно и то же.**

> ⚠️ Сид только апдейтит, но не удаляет: убрать запись из массива недостаточно,
> строку в БД надо удалить руками (или прогнать `db:reset`).

**Решено:** копия тайлов главной живёт в БД (модель `HomeTile`, пункт 3.5), а не
в каталогах сообщений — витрину должно быть можно перекладывать без деплоя.
Значит **4.2 зависит от 3.5**: сначала модель и админка, потом вёрстка главной
поверх неё. Если захочется увидеть плиточную главную раньше, чем будет готова
админка, достаточно засидить несколько `HomeTile` — вёрстка от источника данных
не зависит.

В каталогах сообщений остаётся только служебный текст витрины (навигация,
состояния, ошибки). Названия и описания товаров, как и раньше, в БД.

**~~4.3 — Мобильная адаптивность~~ ✅**

Сделано: `CategoryNav` — шесть категорий сворачиваются в меню ниже `lg`,
переключатели языка и валюты и корзина остаются видимыми на любой ширине.
Пороги в `Tile` подняты с `sm` на `lg`, у высот тайлов появился абсолютный
нижний предел.

Проверялось в iframe'ах фиксированной ширины — окно браузера здесь не меняет
viewport, а iframe меняет, и медиазапросы в нём считаются честно.

Что нашлось и почему пороги именно такие:

- при 375 категории вылезали за экран на целую ширину;
- при 768 всё ещё выталкивали ссылку корзины на 39 px за правый край — поэтому
  порог `lg`, а не `sm`;
- копия тайла вылезала из верхних 39 % кадра и кнопки ложились на устройство.
  Виновата была display-типографика с 640 px: 72 px заголовок + подзаголовок +
  пилюли не помещаются в долю от высоты на низком широком экране. Отсюда
  `lg:text-display` и `max(88svh, 48rem)` / `max(62svh, 42rem)`.

Итог: 160 проверок тайлов на 375/768/1024/1280 × высотах 640–1000 — ни одного
нарушения, горизонтального переполнения нет ни на одной из пяти страниц.

**4.4 — Состояния и качество**

> Добавь везде состояния loading / empty / error (скелетоны, пустой каталог,
> ошибки сети) — все строки в оба каталога сообщений. Переведи картинки на
> next/image. Анимация появления по скроллу: только прозрачность и небольшой
> сдвиг, до ~500 мс, всё под `prefers-reduced-motion`. Прогони проверку
> доступности основных сценариев.

**4.5 — SEO**

> Метаданные (title/description/OpenGraph) на категории и товары для **обеих**
> локалей, `hreflang` между ru и en версиями страницы, sitemap.xml с обоими
> языками и robots.txt. Убедись, что каталог и карточки рендерятся на сервере.

> ✅ Критерий Phase 4: главная выглядит как продуманная витрина, а не как
> вёрстка-заглушка; на телефоне и десктопе ничего не «прыгает»; есть корректные
> состояния и метаданные на двух языках.

## Phase 5 — 3D-слой (вау-надстройка)

**5.1 — Прототип вьюера (изолированно)**

> Сначала прототип отдельно, чтобы оценить сложность. Создай изолированную
> страницу-песочницу с React Three Fiber + @react-three/drei: загрузка тестовой
> .glb модели через useGLTF, освещение через Stage/Environment, вращение
> OrbitControls. Модель — плейсхолдер или своя: мы перепродаём технику Apple, но
> 3D-ассеты Apple не наши, их брать нельзя. Оберни в Suspense с 2D-фолбэком.

**5.2 — 3D на карточке товара**

> Встрой вьюер в product/[slug]: если у товара есть model3dUrl — показываем
> интерактивную 3D-модель, иначе обычную галерею. Ленивая загрузка модели ниже
> первого экрана, отключение при prefers-reduced-motion.

**5.3 — Скролл-герой на главной**

> Сделай верхний тайл главной со скролл-сторителлингом: закреплённая (pinned)
> сцена, модель вращается/собирается по мере скролла через GSAP ScrollTrigger.
> Тайл должен оставаться читаемым и осмысленным, если анимацию убрать совсем.
> Бюджет: модели с Draco-сжатием < 2–3 МБ, clamp dpr, 3D не должен блокировать
> первый рендер и ронять Core Web Vitals.

> ✅ Критерий Phase 5: карточка товара с интерактивной 3D-моделью и эффектная
> главная — при этом Lighthouse-производительность остаётся в норме.
