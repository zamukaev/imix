# iMIX — Промпты для Claude Code (по фазам)

Копируй промпты по порядку. Не перескакивай через фазы: каждый следующий срез
опирается на предыдущий. После каждого крупного шага проверяй результат сам,
прежде чем идти дальше.

## Как этим пользоваться

- Промпты внутри фазы давай **по одному**, не пачкой — так Claude Code не
  распыляется и ты успеваешь ревьюить.
- Полезные приёмы Claude Code:
  - **Plan Mode** (`Shift+Tab` дважды) — сначала пусть распишет план без правок.
  - **Checkpoints** — перед большим шагом; `Esc Esc` откатывает, если что-то сломалось.
  - В конце шага проси прогнать `pnpm typecheck` и `pnpm lint`.
- Если ответ уходит не туда — останови и уточни, не накапливай мусор.

## Phase 1 — Каркас и вертикальный срез

**1.1 — Инициализация монорепо**

> Прочитай CLAUDE.md и ARCHITECTURE.md. Мы в Phase 1. Инициализируй монорепо на
> pnpm workspaces + Turborepo со структурой из ARCHITECTURE.md: apps/web
> (Next.js 15, App Router, TypeScript, Tailwind), apps/api (NestJS + TypeScript),
> packages/types (общие типы) и packages/config (общие пресеты tsconfig/eslint).
> Настрой корневые скрипты pnpm dev / build / typecheck / lint через turbo.
> Пока никакой бизнес-логики — только рабочий скелет, который запускается.

**1.2 — База данных**

> Добавь Prisma в apps/api. Перенеси схему один-в-один из раздела «Data model»
> ARCHITECTURE.md. Создай docker-compose.yml с Postgres для локальной разработки,
> сделай первую миграцию и seed-скрипт: 2 категории (iphone, macbook) и
> 3–4 товара с вариантами и ценами в копейках. Опиши в README, как поднять БД.

**1.3 — Публичное API товаров**

> В apps/api реализуй модули Categories и Products только на чтение:
> GET /categories, GET /products (с фильтром по category и featured, пагинация),
> GET /products/:slug. DTO-типы ответа положи в packages/types и импортируй их
> в контроллерах. Провалидируй query-параметры. Добавь CORS для web.

**1.4 — Витрина: каталог + карточка (срез end-to-end)**

> В apps/web сделай две страницы через Server Components, тянущие данные из API:
> страницу категории (сетка товаров) и страницу товара product/[slug]
> (галерея картинок + выбор варианта + цена, БЕЗ 3D). Используй общие типы из
> packages/types. Свёрстай чисто и минималистично в духе iMIX (оригинальный
> дизайн, не копия Apple). Прогони typecheck и lint.

> ✅ Критерий готовности Phase 1: открываю страницу категории → вижу реальные
> товары из БД → кликаю → карточка товара с вариантами. Весь путь БД → API →
> типы → Next.js работает.

## Phase 2 — Коммерция

**2.1 — Корзина (клиент)**

> Добавь корзину на Zustand в apps/web: добавить/убрать вариант, изменить
> количество, посчитать итог на клиенте. Персист корзины в localStorage.
> Страница /cart со списком позиций и итогом.

**2.2 — Auth**

> Реализуй в API auth-модуль: register, login, refresh на JWT (access + refresh),
> хэш паролей (argon2 или bcrypt), guard'ы и роль USER/ADMIN. На web — простые
> формы входа/регистрации и хранение токена. Middleware, добавляющее токен к
> запросам к API.

**2.3 — Заказы + Stripe**

> Реализуй оформление заказа. POST /orders: проверяет наличие на складе,
> пересчитывает итог из БД (клиентским ценам не доверяем), создаёт заказ PENDING.
> POST /payments/intent возвращает client secret Stripe. На web — страница
> /checkout со Stripe Elements. Реализуй вебхук POST /payments/webhook: по
> payment_intent.succeeded переводит заказ PENDING → PAID и списывает сток
> в транзакции. GET /orders/me для истории.

> ✅ Критерий: могу пройти путь товар → корзина → checkout → тестовая оплата
> Stripe → заказ становится PAID, сток уменьшился.

## Phase 3 — Админка

**3.1 — Защита и каркас**

> Создай защищённую группу роутов app/(admin) в web. Middleware пускает только
> роль ADMIN, API-эндпоинты админки тоже под role-guard (клиенту не доверяем).
> Свёрстай layout админки и страницу-дашборд с базовой статистикой
> (кол-во товаров, заказов, выручка).

**3.2 — CRUD товаров и категорий**

> Реализуй в API админские эндпоинты POST/PATCH/DELETE для products, их variants
> и categories. Эндпоинт POST /upload для загрузки картинок (и позже .glb) в
> Cloudinary или S3 — вынеси провайдер за интерфейс. На web — страницы админки:
> список товаров, форма создания/редактирования с вариантами и загрузкой картинок.

**3.3 — Заказы в админке**

> GET /admin/orders + страница списка заказов в админке с фильтром по статусу и
> возможностью сменить статус (например, PAID → SHIPPED).

> ✅ Критерий: под админом создаю товар с картинками и вариантами → он появляется
> в витрине; вижу входящие заказы и меняю их статус.

## Phase 4 — Адаптив и полировка

**4.1 — Мобильная адаптивность**

> Пройди все страницы витрины и сделай их адаптивными (мобайл-фёрст): хедер с
> мобильным меню и корзиной, сетка каталога, карточка товара, корзина, checkout.
> Проверь на ширинах 375 / 768 / 1280.

**4.2 — Состояния и качество**

> Добавь везде состояния loading / empty / error (скелетоны, пустой каталог,
> ошибки сети). Оптимизируй картинки через next/image. Прогони проверку
> доступности базовых сценариев.

**4.3 — SEO**

> Добавь метаданные (title/description/OpenGraph) на страницы категорий и
> товаров, sitemap.xml и robots.txt. Убедись, что каталог и карточки
> рендерятся на сервере для индексации.

> ✅ Критерий: сайт удобен и целен на телефоне и десктопе, ничего не «прыгает»,
> есть корректные состояния и метаданные.

## Phase 5 — 3D-слой (вау-надстройка)

**5.1 — Прототип вьюера (изолированно)**

> Сначала прототип отдельно, чтобы оценить сложность. Создай изолированную
> страницу-песочницу с React Three Fiber + @react-three/drei: загрузка тестовой
> .glb модели через useGLTF, освещение через Stage/Environment, вращение
> OrbitControls. Модель — плейсхолдер/оригинальная, не ассеты Apple. Оберни в
> Suspense с 2D-фолбэком.

**5.2 — 3D на карточке товара**

> Встрой вьюер в product/[slug]: если у товара есть model3dUrl — показываем
> интерактивную 3D-модель, иначе обычную галерею. Ленивая загрузка модели ниже
> первого экрана, отключение при prefers-reduced-motion.

**5.3 — Скролл-герой на главной**

> Сделай на главной секцию со скролл-сторителлингом: закреплённая (pinned) сцена,
> модель вращается/собирается по мере скролла через GSAP ScrollTrigger.
> Бюджет производительности: модели с Draco-сжатием < 2–3 МБ, clamp dpr, 3D не
> должен блокировать первый рендер и ронять Core Web Vitals.

> ✅ Критерий: карточка товара с интерактивной 3D-моделью и эффектная главная —
> при этом Lighthouse-производительность остаётся в норме.
