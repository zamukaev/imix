# iMIX — Промпты для Claude Code (по фазам)

Копируй промпты по порядку. Не перескакивай через фазы: каждый следующий срез
опирается на предыдущий. После каждого крупного шага проверяй результат сам,
прежде чем идти дальше.

## Как этим пользоваться

- Промпты внутри фазы давай **по одному**, не пачкой — так Claude Code не
  распыляется и ты успеваешь ревьюить.
- Полезные приёмы Claude Code:
  - **Plan Mode** (`Shift+Tab` дважды) — сначала пусть распишет план без правок.
  - **Checkpoints** — перед большим шагом; `Esc Esc` откатывает, если что-то сломалось.
  - В конце шага проси прогнать `pnpm typecheck` и `pnpm lint`.
- Если ответ уходит не туда — останови и уточни, не накапливай мусор.
- Промпты ниже намеренно не повторяют то, что уже написано в `CLAUDE.md` и
  `ARCHITECTURE.md`. Достаточно попросить прочитать нужный раздел.

## Phase 3 — Админка ◄ текущая

**~~3.1 — Auth~~ ✅**

Сделано: в API модуль `auth` — register / login / refresh / me на двух JWT
(access 15 мин, refresh 30 дней, **разные секреты**), argon2, `JwtAuthGuard`,
`OptionalJwtAuthGuard`, `RolesGuard` + `@Roles()` и `@CurrentUser()`. Первый
ADMIN приходит из сида (`ADMIN_EMAIL` / `ADMIN_PASSWORD`) — через API роль не
получить, DTO регистрации поля `role` не знает и отвергает его.

На web — страницы `/login` и `/register` на обеих локалях, сессия в двух
httpOnly-куках, аккаунт в шапке. `GET /orders/me` есть, страницы для него пока
нет — она в 3.2.

Три решения, которые стоит помнить:

- **Токены не ставит API.** Он отдаёт их в теле, куки ставит уже web через свои
  route handlers в `app/api/auth/*`. Причина простая: разные origin'ы, и куке от
  API понадобился бы `SameSite=None; Secure` — локально это не работает.
- **Подпись на стороне web не проверяется** (`lib/jwt-claims.ts`). Секрет живёт
  только в API, а он проверяет каждый запрос; на витрине это UX-гейт — решает,
  какую ссылку показать в шапке, и ничего больше.
- **Middleware пришлось тронуть уже здесь**, вопреки плану: Server Component не
  может выставить куку, поэтому продлевать сессию больше негде. Без этого через
  15 минут шапка показывала бы «Войти» живой сессии. Гейт роли для `/admin`
  встанет рядом в 3.2.

> ⚠️ Refresh-токен без таблицы: отозвать одну сессию нельзя, только сменить
> `JWT_REFRESH_SECRET` и разлогинить всех. Осознанный размен на время MVP.

**~~3.2 — Защита и каркас админки~~ ✅**

Сделано: `GET /admin/stats` под `JwtAuthGuard` + `RolesGuard` — guard'ы висят на
**контроллере**, а не на методах, чтобы новый роут в `/admin` был закрыт по
умолчанию. Группа роутов `app/[locale]/(admin)/admin` со своим layout'ом (без
витринной шапки: админка — инструмент, язык тайлов из §5 сюда не относится) и
дашборд: каталог, заказы по статусам, выручка **отдельной карточкой на каждую
валюту**.

Три момента:

- **Три слоя защиты, и только один из них решает.** Middleware редиректит,
  layout проверяет ещё раз на сервере, API отдаёт 403 — настоящий из них
  последний. Пройти первые два = получить пустую оболочку, где каждый запрос
  отвечает 403.
- **Два разных отказа.** Не залогинен → `/login?next=…` с сохранением локали и
  query. Залогинен, но не ADMIN → на главную: просить его войти ещё раз
  бессмысленно, он уже вошёл. `next` проверяется (`safeReturnTo`) — форма
  логина, которая идёт куда сказано, это open redirect.
- **Выручка считается только по PAID и SHIPPED.** PENDING — брошенная корзина,
  FAILED и CANCELLED — деньги, которые не двигались. И суммы по валютам нигде
  не складываются: общей цифры на странице нет вообще.

> ⚠️ Роль лежит внутри access-токена, поэтому смена роли вступает в силу не
> раньше, чем истечёт текущий (15 минут) или пользователь перелогинится. Это
> цена того, что guard не ходит в БД на каждый запрос.

**~~3.3 — CRUD товаров и категорий~~ ✅**

Сделано: POST/PATCH/DELETE для категорий, товаров и вариантов, `POST /admin/upload`
с провайдером за интерфейсом `AssetStorage`, на web — список товаров, форма
создания/редактирования с вариантами и загрузкой картинок, страница категорий.
48 новых тестов (41 e2e на каталог, 7 на загрузку) + 45 юнит-тестов на формы.

Что решено по ходу, и почему:

- **Базовые цены выводятся, а не вводятся.** `basePriceRub/Usd` — это минимум по
  вариантам, пересчитывается при любом изменении вариантов. Дать админу вводить
  их руками значило бы разрешить сетке каталога расходиться с тем, что берёт
  корзина. Минимум берётся **по каждой валюте отдельно**: списки заданы вручную и
  не обязаны согласовываться в том, какой вариант дешевле.
- **Товар нельзя создать без вариантов** — иначе он встанет в каталог с ценой 0.
  Поэтому вариант приходит вместе с товаром одним запросом; при редактировании
  каждый вариант сохраняется отдельно, потому что каждое изменение двигает
  выведенные цены и ответ приносит товар целиком.
- **Удаление защищает историю заказов.** Товар или вариант, который уже покупали,
  удалить нельзя (409, `OrderItem` ссылается на вариант) — вместо этого обнуляем
  остаток. Последний вариант тоже не удаляется. Категорию с товарами — тоже нет.
- **Форма работает в рублях, а не в копейках.** `lib/money-input.ts` конвертирует
  на границе, целочисленно (`19.99 * 100` — это 1998.9999999999998), принимает и
  запятую: русская раскладка даёт именно её. 21 тест — потерянные два нуля
  означают телефон за 1 499 ₽.
- **Расширение берётся из просмотренного типа, не из имени файла.** Имя — та
  половина загрузки, которую пишет атакующий. Файл называется хешем содержимого,
  поэтому одна и та же фотография дважды — это один файл.

> ⚠️ Без `CLOUDINARY_URL` загрузка пишет в `apps/web/public/uploads` и работает,
> только пока API и витрина делят диск. Это dev-режим, и он честно предупреждает
> об этом в логе. Продакшену нужен `CLOUDINARY_URL` — код при этом не меняется.

**~~3.4 — Заказы в админке~~ ✅**

Сделано: `GET /admin/orders` с фильтром по статусу и постраничностью,
`PATCH /admin/orders/:id`, страница `/admin/orders` — фильтр живёт в URL, сумма
всегда стоит рядом со своей валютой. 19 e2e-тестов.

Три вещи, которые стоит помнить:

- **Админ не может поставить PAID или FAILED.** Их пишет платёжный вебхук.
  Разрешённые переходы лежат в `ADMIN_ORDER_TRANSITIONS` в `@imix/types` — один
  список на обе стороны: UI показывает ровно те кнопки, которые API примет.
  SHIPPED и CANCELLED — финальные.
- **Отмена оплаченного заказа возвращает остаток.** Вебхук списал его при оплате
  (`PaymentsService.markPaid`), и без возврата отмена тихо теряла бы товар,
  который никто не купил. В той же транзакции и с условием на текущий статус,
  чтобы два одновременных нажатия не вернули остаток дважды. Отмена PENDING
  остаток **не** трогает: он тогда и не списывался.
- **Список переиспользует `OrdersService`,** а не заводит второй маппер. То, что
  видит покупатель на странице подтверждения, и то, что видит админ в списке, —
  это одни и те же строки; расхождение здесь означало бы расхождение в сумме.

**~~3.5 — Редактируемая главная~~ ✅**

Сделано ранее (до границы авторизации): модель `HomeTile` + две миграции,
публичный `GET /home-tiles?locale=`, сид тайлов, баннеры в
`apps/web/public/home/`. Теперь дописана вся write-часть: `GET/POST/PATCH/DELETE
/admin/home-tiles` и `POST /admin/home-tiles/:id/move`, страницы
`/admin/home-tiles` со списком и порядком плюс форма тайла. 38 e2e-тестов.

- **Ссылки проверяются по реальному каталогу.** `/phones` проходит, только если
  такая категория есть; `/product/x` — только если есть товар. Отвергаются
  `/en/phones` (префикс локали витрина добавляет сама), внешние адреса, пути
  глубже одного сегмента и query-строки. Это тот самый пункт, который в
  `ARCHITECTURE.md` §2 был помечен как «пока не проверяется».
- **Кнопка — всё или ничего.** Витрина молча выбрасывает наполовину заполненную
  CTA, и для уже лежащей строки это правильно. Но для правки, которую человек
  делает прямо сейчас, — нет: он нажмёт «сохранить» и увидит, что ничего не
  появилось. Поэтому на запись API требует оба языка и ссылку либо пусто.
- **Перестановка переписывает весь список** (`(index+1)*10`), а не меняет два
  числа местами. `position` намеренно не уникален, коллизия — реальное
  состояние, и обмен одинаковых чисел выглядел бы как сломанная кнопка.
- Новый тайл создаётся **черновиком** и встаёт в конец: витрина меняется, когда
  человек это решил, а не когда начал печатать.

> ✅ **Критерий Phase 3 выполнен** — проверено на живой системе: под админом
> создаю товар с картинками, вариантами, ценами в двух валютах и текстами на
> двух языках → он появляется в витрине на обоих языках; вижу входящие заказы и
> меняю их статус; меняю порядок тайлов на главной без деплоя.

**~~4.2.1 — Расширение каталога~~ ✅**

Сделано: 6 категорий (добавлены `tablets`, `watches`, `audio`, `accessories`),

> ⚠️ Тайл AirTag не сделан намеренно. Единственное его фото — квадратный

> на устройство. Вместо этого тайл AirPods остаётся без пары и рисуется во всю
> ширину — ровно тем правилом, что заложено в `toHomeRows`. **Кадр для тайла и
> предметная съёмка — не одно и то же.**

> ⚠️ Сид только апдейтит, но не удаляет: убрать запись из массива недостаточно,
> строку в БД надо удалить руками (или прогнать `db:reset`).

**Решено:** копия тайлов главной живёт в БД (модель `HomeTile`, пункт 3.5), а не
в каталогах сообщений — витрину должно быть можно перекладывать без деплоя.
Значит **4.2 зависит от 3.5**: сначала модель и админка, потом вёрстка главной
поверх неё. Если захочется увидеть плиточную главную раньше, чем будет готова
админка, достаточно засидить несколько `HomeTile` — вёрстка от источника данных
не зависит.

В каталогах сообщений остаётся только служебный текст витрины (навигация,
состояния, ошибки). Названия и описания товаров, как и раньше, в БД.

**~~4.3 — Мобильная адаптивность~~ ✅**

Сделано: `CategoryNav` — шесть категорий сворачиваются в меню ниже `lg`,
переключатели языка и валюты и корзина остаются видимыми на любой ширине.
Пороги в `Tile` подняты с `sm` на `lg`, у высот тайлов появился абсолютный
нижний предел.

Проверялось в iframe'ах фиксированной ширины — окно браузера здесь не меняет
viewport, а iframe меняет, и медиазапросы в нём считаются честно.

Что нашлось и почему пороги именно такие:

- при 375 категории вылезали за экран на целую ширину;
- при 768 всё ещё выталкивали ссылку корзины на 39 px за правый край — поэтому
  порог `lg`, а не `sm`;
- копия тайла вылезала из верхних 39 % кадра и кнопки ложились на устройство.
  Виновата была display-типографика с 640 px: 72 px заголовок + подзаголовок +
  пилюли не помещаются в долю от высоты на низком широком экране. Отсюда
  `lg:text-display` и `max(88svh, 48rem)` / `max(62svh, 42rem)`.

Итог: 160 проверок тайлов на 375/768/1024/1280 × высотах 640–1000 — ни одного
нарушения, горизонтального переполнения нет ни на одной из пяти страниц.

**~~4.4 — Состояния и качество~~ ✅**

Сделано: скелетоны (`loading.tsx` для главной, каталога, карточки товара и
админки), границы ошибок (`error.tsx` для витрины и для админки), пустая
главная, `next/image` везде, `Reveal` по скроллу, аудит доступности.

- **Скелетон повторяет форму того, что заменяет** — квадрат там, где будет
  фотография. Иначе страница прыгает в момент подмены. Пульс под
  `motion-safe:`, объявление одно на экран (`LoadingScreen`), сами блоки скрыты
  от скринридера: сетка из двенадцати карточек не должна читаться двенадцать раз.
- **`Reveal` начинается видимым.** Скрытие ставит эффект, который выполняется
  только в браузере, — поэтому в серверном HTML, у краулера и без JS контент на
  месте. Проверено: `opacity-0` в отданном HTML встречается 0 раз. При
  `prefers-reduced-motion` анимации нет вообще, а не «покороче»; элемент над
  сгибом не прячется и не проявляется.
- **`next/image`:** 180 КБ JPEG → 1 КБ WebP на 640px (проверено на живом
  оптимизаторе). У каждой картинки свой `sizes`, у Cloudinary — явный
  `remotePatterns`, а не звёздочка: этот список и есть то, что не даёт указать
  оптимизатор магазина на чужой сервер.

Аудит доступности нашёл четыре реальные вещи, все исправлены:

| Что | Было | Стало |
| --- | --- | --- |
| Уровни заголовков в каталоге | `h1` → `h3` | `h1` → `h2` |
| Главная | без `<main>` | `<main id="main-content">` |
| Обход шапки | нет | skip-link первым в порядке табуляции |
